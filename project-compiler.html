The problem

Compiler concepts are easy to memorize and much harder to understand as a connected system. The project became a way to make each stage visible and inspectable instead of treating compilation as one opaque step.

The solution

I separated the compiler into explicit stages — lexical analysis, parsing, syntax structure, intermediate representation, and feedback — then connected those stages to a small interface that makes the output of each step easier to inspect.

Engineering decisions

Stage separationLexing, parsing, AST construction, and IR generation stay conceptually separate so each stage can be tested and reasoned about.
Feedback mattersSyntax problems are surfaced close to the source rather than only appearing as a final generic error.
Inspectable outputTokens, syntax structure, and intermediate output are visible so the compiler can be used as a learning and debugging tool.

System flow

The project is easiest to understand as a flow of responsibilities rather than a single screen.

Source code→Tokenizer→Parser / AST→IR / feedback

What I’d improve next

Add a richer grammar and more language constructs.
Introduce semantic analysis and a symbol table.
Add stronger error recovery so parsing can continue after some errors.
Add automated compiler-stage tests and fixture programs.

What I learned

Building the stages separately made the pipeline much easier to understand. It also showed me why useful compiler errors are a product problem as much as a parsing problem: the system has to explain what went wrong in a way the developer can act on.
