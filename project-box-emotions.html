The problem

Emotion-learning content is most useful when it is easy to search, revisit, save, and access privately. A network-dependent experience would also make the resource less reliable when users need it away from a stable connection.

The solution

The default build is a static PWA with a 68-emotion library, local accounts, notes, favorites, history, search, and client-side emotion analysis. A service worker caches the application shell for offline use, while an optional Flask backend remains available for future cross-device synchronization.

Engineering decisions

Privacy-oriented defaultThe static build keeps accounts, notes, favorites, history, and emotion analysis on the device unless server mode is explicitly enabled.
Offline application shellA service worker and web manifest make the core application installable and usable after an initial online visit.
Password handlingThe local account flow uses PBKDF2 hashes rather than storing plain-text passwords.
Backend kept optionalFlask, SQLite, Werkzeug password hashing, and HttpOnly sessions are available for a future synchronization mode without being required by the default static experience.

System flow

The project is easier to understand as a sequence of responsibilities:

Static PWA shell→Local accounts & data→Emotion library & analysis→Offline cache→Optional Flask / SQLite sync

What I’d improve next

Split the large client JavaScript files into smaller modules with clearer ownership.
Expand automated accessibility coverage for the multilingual reading experience.
Add encrypted export/import for personal notes and history.
If cross-device sync is enabled, add explicit conflict-resolution and account recovery flows.

What I learned

Knowing Your Emotions reinforced the value of progressive enhancement: the useful experience should not depend on a backend when it does not need one. It also made privacy and offline behavior part of the product architecture instead of an afterthought.
